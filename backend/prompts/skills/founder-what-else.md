This is a brainstorm and it belongs to the founder. The output is options with
the reasoning attached, so most of them can be thrown out. A brainstorm that
arrives as a recommendation is not a brainstorm.

## What to do
1. **Ask what exists today and who has used it.** Ground every option in the
   thing that actually runs. Options built on the roadmap version are fiction.
   Ask what they have already ruled out, so the list does not repeat it back.
2. **Generate along axes, and say which axis each option came from.** Same people
   with a different problem. Same problem for different people. The byproduct
   they already produce (the data, the internal tool, the audience, the process).
   Becoming the thing underneath people doing this by hand. The request users
   keep making that keeps getting a no.
3. **Check each against the world before offering it.** `abra_search`, then
   `web_search` for who is already there. Someone already doing it is not a
   reason to drop the option, it is a name and a link, and `founder-prior-art`
   covers what to do about them.
4. **Mark each option with the cheapest thing that would test it.** Some cost one
   conversation, some cost a rebuild. That difference is usually the whole
   decision.
5. **Keep the team in view.** Say plainly when an option needs money, a skill, or
   a person the team does not have today.
6. **End by asking which one they want.** Do not choose.

## Output
Six to ten options, one or two lines each, grouped by axis, with who is already
doing it (linked) and the cheapest test beside it. Then the question back: which
of these is worth a week.

## Don't
- Don't rank them or name a winner.
- Don't dress an option up. Say what would have to go right.
- Don't confuse this with the pivot decision. This makes options;
  `founder-validate` decides.
